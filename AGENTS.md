# AGENTS.md

Planora is a pnpm + Turborepo monorepo: a Discord bot (`apps/bot`), a TanStack Start web app (`apps/web`), and shared packages under `packages/`. Package manager is pnpm 12 (`packageManager` in root `package.json`); do not use npm or yarn.

## Commands

Run from the repo root unless noted.

- Install: `pnpm install --frozen-lockfile`
- CI order (`.github/workflows/ci.yml`): `pnpm build` -> `pnpm lint` -> `pnpm typecheck` -> `pnpm test`. Root scripts run through `turbo`.
- Lint/format: Biome only (no ESLint or Prettier). `pnpm lint` checks, `pnpm fix` writes fixes.
- Single package: `pnpm --filter bot test`, `pnpm --filter bot typecheck`, `pnpm --filter @workspace/db migrate`
- Single test file: `pnpm --filter bot exec vitest run src/shared/utils/time.test.ts` (`pnpm --filter bot test` runs the whole bot suite)
- Dev: `pnpm --filter bot dev` (tsx watch, loads `apps/bot/.env`), `pnpm --filter web dev`
- Production start: `node apps/bot/dist/index.mjs` (bot), `node apps/web/dist/server/index.mjs` (web), after `pnpm build`
- Tests currently run without Postgres or Redis; they mock the logger and DB/Redis-backed services.

## Layout and entrypoints

- `apps/bot/src/index.ts` is a thin entrypoint: `createClient()` from `app/client.ts` (intents, partials, error hook) then `createLifecycle(client)` from `app/lifecycle.ts`. Lifecycle startup is `registerEvents(client)` then `client.login` then session sweeper start. Shutdown on SIGINT/SIGTERM closes the sweeper, session write sink, Discord client, Redis, and DB. Any new long-lived resource must be wired into this shutdown path.
- `apps/bot/src/core/`: framework (event/component loaders, component registry, command registry, command types, logger). `apps/bot/src/features/<feature>/` holds feature code (`commands/`, `events/`, `components/`, `services/`, `sweeper/`, `utils/`, plus feature-local helpers such as `activity/{identity,tracking,reporting}`). `apps/bot/src/shared/` holds shared utilities, `discord/` helpers (interaction errors, profile guard), pagination kit, and constants.
- `apps/web`: TanStack Start + Vite + Nitro. `src/routes/` holds file-based routes. `src/routeTree.gen.ts` is generated by the router plugin, gitignored, and excluded from Biome; never hand-edit it.
- `packages/db`: Drizzle ORM on Postgres (`pg`, native driver). Schema is in `src/schema/`. Exports `db`, `closeDb`, and re-exports `drizzle-orm`.
- `packages/env`: typed env validation (`@t3-oss/env-core` + zod). `@workspace/env` for bot/redis/logger; `@workspace/env/db` for db and `drizzle.config.ts`.
- `packages/redis`: ioredis singleton with helpers. Most helpers fail open (log and return a default) on Redis errors; `getJsonStrict` and `scanKeys` throw.
- `packages/logger`: pino. Use `createChildLogger(name)`.
- `packages/ui`: shadcn components. Import as `@workspace/ui/components/button`. Add components with `pnpm dlx shadcn@latest add button -c apps/web`; the code lands in `packages/ui/src/components`.
- Workspace packages export `src` under the `development` condition and `dist` otherwise. The bot and web tsconfigs use `customConditions: ["development"]`.

## Bot conventions (non-obvious)

- Feature modules are auto-discovered by glob (`core/loaders/feature-modules.ts`): any `.ts`/`.js`/`.mjs` under `features/**/{commands,events,components}/` is loaded, excluding `*.test.*`, `*.spec.*`, and `__tests__/**`. Put new handlers in those folders, or they are never registered.
- Exports are duck-typed, not registered by name:
  - Commands need `data` and `execute`.
  - Events need `event` and `execute`. Listeners run sorted by `priority` (default 50). Returning `false` stops the chain. Errors are logged per listener. `execute` must return `boolean | undefined` (or a promise of them); do not pass a `Promise<void>` helper directly — wrap it (`execute: async (client) => { await registerCommands(client) }`).
  - Components need `kind` (`"button"` or `"modal"`), `feature`, `match`, and `onButton` or `onModal`; `ownerOnly` is optional. Files with no matching export are skipped, with a warning for components.
- A priority-5 `interaction-create` listener calls `dispatchComponent`; command dispatch is priority 10. Component customIds are always `<feature>:<sessionId>[:rest]`.
- Import rule: in `apps/bot`, use the `@/` alias for source imports. Relative `./` and `../` imports are a Biome error (`biome.json` override).
- Interactive views (buttons and modals) go through `componentRegistry.openView`, which owns the button collector, owner checks, expiry timer, and one open view per feature/session. Modal submits route to the view's `onModal` only when the full `<feature>:<sessionId>` matches. Pagination uses this path; do not add private collectors or `awaitModalSubmit`.
- Commands that target a user call `viewProfile` from `shared/discord/profile-view.ts`. It owns visibility resolution, defer, the ephemeral flag, and deny copy; commands keep only their own error `editReply`. The command injects `resolveProfileVisibility` because `shared/**` must never import `features/**`; keep that dependency direction when adding shared helpers.
- Commands deploy on `ClientReady` via `registerCommands` in `core/commands/registry.ts`. With `DISCORD_DEV_GUILD_ID` set, deployment is guild-scoped and skipped if that guild is not cached; unset deploys globally. Leave the variable unset in the production root `.env`.
- `shared/**` may import `@workspace/*` and `discord.js`; it must never import `features/**`. `shared/pagination` is the one allowed `core/**` import (`@/core/components/registry`) because the kit is built on the registry; do not add more. Feature code imports its own leaves directly; the feature-root barrels exist only for cross-feature imports (`activity → system`).
- `tsdown` builds `apps/bot/src` minus tests, so tests stay out of `dist`.

## Testing

- Vitest config is `apps/bot/vitest.config.ts`: `include` is `src/**/*.test.ts`, setup file is `src/test/setup.ts`, `@/` alias is set.
- `src/test/setup.ts` sets default env values (`NODE_ENV=test`, `LOG_LEVEL=fatal`, dummy `DATABASE_URL`, `REDIS_URL`, `DISCORD_BOT_TOKEN`), so env validation passes in tests.
- Test helpers and fakes are in `apps/bot/src/test/` (`fakes/` for Discord interactions, messages, and collectors; `pagination-helpers.ts`). `FakeChatInputCommandInteraction` accepts `guildId`; pass `null` for DM behavior. It also implements `fetchReply()`, which `/ping` latency math needs.
- Existing tests mock `@/core/logger` with `vi.mock`. Follow that pattern for new tests.

## Environment and config

- Env is read from `process.env` and validated at import time by `@t3-oss/env-core`. Importing `@workspace/env`, `@workspace/db`, or `@workspace/redis` without the required vars throws.
- Env files are gitignored. Use `.env.example` as the template:
  - Root `.env`: used by `docker compose` (`docker-compose.yml`), including `LOKI_URL`.
  - `apps/bot/.env`: local bot runs (`dev` uses `tsx --env-file=.env`). Set optional `DISCORD_DEV_GUILD_ID` here for instant guild-scoped command deployment; leave it unset in production.
  - `packages/db/.env`: `DATABASE_URL` for drizzle-kit commands.
- `packages/db` throws at import if the `pg-native` binding cannot load. The Dockerfiles install `libpq-dev`/`libpq5` for this.

## Database and schema

- Schema source of truth: `packages/db/src/schema/` (Postgres dialect, `drizzle.config.ts` points there).
- Migration flow: change the schema, run `pnpm --filter @workspace/db generate`, read the generated `migration.sql`, commit the schema change and the migration together, then run `pnpm --filter @workspace/db migrate`. `packages/db/migrations/` holds one tracked Postgres baseline, `20261026141134_glamorous_veda` (`migration.sql` + `snapshot.json`); it must stay tracked because `snapshot.json` is the diff base for the next `generate`.
- Never edit an applied migration — fix forward with a new one. `push` diffs against a live database and can drop data; keep it for throwaway databases only.
- Drizzle commands: `generate`, `migrate`, `push`, `studio` (scripts in `packages/db/package.json`).

## Deployment

- `apps/bot/Dockerfile` and `apps/web/Dockerfile`: multi-stage, `turbo prune <app> --docker`, `pnpm install --frozen-lockfile`, `turbo build`, non-root runner. Dockerfiles and CI both use Node 24 (`.nvmrc`-free; `engines.node` is `>=24`).
- `docker-compose.yml` (project name `planora`) runs `web`, `bot`, and `promtail` (ships container logs to Loki).
- Bot command deployment happens at `ClientReady`; restarting the bot replaces the command payload. Global command changes can take up to an hour to propagate in Discord, guild commands are immediate.

## Style and conventions

- Biome config: tabs, indent width 3, line width 80, double quotes, no semicolons, ES5 trailing commas, LF line endings. Import sorting is on. Class strings passed to `cn`/`cva` are sorted by a Biome rule.
- Commits use Conventional Commits with a scope, e.g. `feat(bot): ...`, `fix(bot): ...`, `test(bot): ...`, `chore: ...`, `ci: ...`.
- `TODO.md` at the root is a gitignored personal review log. Its open/closed items are not verified against code, so do not treat them as spec.
